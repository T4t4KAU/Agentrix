# KV 内存管理：生命周期、分支共享与分层缓存

长生命周期推理需要同时控制活动工作集、可复用状态、备份空间和工具中间数据。
Agentrix 采用应用语义驱动的策略层，复用官方 APC、分页共享和卸载连接器；
设备搬运由对应后端完成。工具数据管理、选择性备份策略和容量评价方法属于
框架层，CUDA 与 Ascend 分别验证后端成本和收益范围。

当前已有收益包括工具正文按需加载、不可变页面共享、阶段回收、有界流式入库，
以及已知终止请求的选择性 KV 备份。H100 与 Ascend 均已验证恢复延迟和较小
设备池的容量取舍；增长上下文的收益限定于已测串行场景。工具等待主动迁移、
恢复前预取和通用磁盘 KV 分层尚未完成。

## 度量对象与比较方法

| 指标 | 衡量对象 | 解释边界 |
| --- | --- | --- |
| 活动 KV 工作集 | 当前被请求或传输引用的物理块 | 共享页只计一次；不等于预分配池大小 |
| 可回收前缀缓存 | 无活跃引用但仍可命中的页及混合状态 | 可以复用，也可能被新分配覆盖 |
| 设备 KV 预算与 HBM 峰值 | 配置池大小及板卡实际采样占用 | 固定池内释放块不自动向设备归还 HBM |
| CPU KV 预算与读写量 | 主存备份空间及累计搬运 | 配置预算、有效载荷、PSS 和传输字节分别统计 |
| 工具页面与进程 RSS | 原始快照、共享存储及临时分配 | 与模型派生 KV 分开核算 |
| 恢复 TTFT 与任务耗时 | 再次请求时的首 token 延迟及完成时间 | 容量收益须同时报告延迟和额外资源成本 |

实验采用相同模型、输入计划、输出预算与请求依赖，对照原生 APC、官方普通
CPU 备份和相同预算下的选择性备份。缓存压力由正常请求产生；增长轨迹内部
不清空缓存。两个种子的重复测量先分别汇总，再等权合并，变化率由合并值计算。
收益表列出已建立收益的配置及必要基线，不代表完整矩阵的总体成功率。

## Agent Hints 与选择性备份

应用在派发时明确知道某请求不会再被复用，才设置
`kv_transfer_params.max_offload_tokens=0`；其他请求保持官方默认。
这样避免终止请求的新备份挤掉稍后需要恢复的会话，减少 CPU 写入与恢复重算。
该字段不会删除已有副本、禁止读取已有缓存或主动释放设备显存。
参见 [官方选择性卸载接口](https://docs.vllm.ai/en/latest/features/kv_offloading_usage/#per-request-selective-offload)。

会话身份使用官方 `X-Session-ID` 与 `consistent_hash`。应用入口为
[session_kv_options](../application/src/agentrix_application/session_kv.py)。
一次回复结束、一次工具调用开始或一个子分支结束，都不足以证明共享前缀再无
消费者；未知复用关系时不标记终止。提示仅使用当时的应用状态，不从未来轨迹
反推在线策略。

普通 HTTP 请求完成后，引擎已经释放请求引用，无其他使用者的块可被后续分配
覆盖；再执行一次释放通常不会增加可用容量。CPU 备份的价值是为这些可回收页
保留恢复来源，而不是把逻辑会话结束等同于 HBM 归还。

[AgentX 文章](https://vllm.ai/blog/2026-09-08-vllm-agentx#the-path-ahead-planned-optimizations-and-future-work)
讨论了生命周期提示、工具等待和预取。当前实现覆盖其中的终止语义与选择性
备份，尚未形成工具等待期间迁移、返回前预取的完整控制流程。
官方 [Program scheduling](https://github.com/vllm-project/router/blob/main/docs/program_scheduling.md)
的逻辑准入也应与引擎物理 KV 操作区分，不能据逻辑容量释放推断显存下降。

## CUDA H100：恢复延迟与设备容量

使用 Qwen3.5-9B BF16、FlashAttention 3、eager、同步调度、Mamba `align`，
最大上下文 16,384、最大序列数 8、batch token budget=8,192；CPU 层为官方
`OffloadingConnector` 与 LRU。每轮准备四个待恢复会话，插入八个已知终止
请求，再恢复原四个会话。每个输入 8,192 token、固定输出 16 token。
两个种子各三轮，交换策略顺序，比较相同输入与生成输出。

| 同为 2 GiB GPU + 2 GiB CPU | 官方默认卸载 | 选择性备份 |
| --- | ---: | ---: |
| 恢复请求数 | 24 | 24 |
| 平均恢复 TTFT | 460.96 ms | 136.90 ms |
| P95 恢复 TTFT | 475.34 ms | 163.59 ms |
| 恢复重算 token，总计 | 196,608 | 6,528 |
| 终止请求 CPU 写入，每轮 | 2.317 GiB | 0 |
| 恢复 CPU 读回，每轮 | 0 | 1.159 GiB |
| 板卡显存采样峰值 | 21,904.56 MiB | 21,904.56 MiB |

相同预算下，选择性备份使恢复重算减少 **96.68%**，平均恢复 TTFT 降低
**70.30%**。实际 CPU 读回说明可复用副本得以保留；板卡显存相同，收益来自
更有效地使用备份空间，不来自设备池缩小。

进一步比较满足恢复 P95 不超过 300 ms 的配置：

| GPU KV 池 | 策略 | CPU KV 预算 | 平均恢复 TTFT | 恢复 P95 | HBM 采样峰值 |
| --- | --- | ---: | ---: | ---: | ---: |
| 2 GiB | 选择性备份 | 2 GiB | 136.90 ms | 163.59 ms | 21,904.56 MiB |
| 1 GiB | 选择性备份 | 2 GiB | 139.60 ms | 164.20 ms | 20,944.56 MiB |
| 0.75 GiB | 选择性备份 | 2 GiB | 139.51 ms | 167.27 ms | 20,688.56 MiB |
| 4 GiB | 无卸载 APC | 0 | 115.14 ms | 163.24 ms | 23,750.56 MiB |

0.75 GiB 选择性备份相对 4 GiB APC，设备 KV 配置预算降低 **81.25%**，
板卡显存采样峰值减少 **3,062 MiB**；代价为额外 2 GiB CPU 预算，以及
平均恢复 TTFT 增加 **24.37 ms**。两者满足同一门槛，不代表延迟完全相同。

0.75 GiB 是最低已测达标配置，未扫描 APC 的 2～4 GiB 中间档位，也未测
最大活跃并发。当前混合模型恢复结论限于已测输入和状态边界，不推广到任意
部分尾块。容量扫描是比较方法，不是新增内存管理算法。

## Ascend：选择性备份与双卡容量

单卡实验采用 Qwen3.5-9B BF16、910B2、eager、同步调度、2 GiB 设备 KV
和 2 GiB CPU KV。每轮四个保留会话、八个终止请求、四次恢复，输入
8,193 token、输出 16 token；两个种子各三轮。模型同时恢复 attention 页
与对应 GDN 状态，每次恢复 8,192 token、重算末尾一个 token。

| 指标 | 普通 CPU 卸载 | 选择性备份 |
| --- | ---: | ---: |
| 恢复平均 TTFT | 794.16 ms | 192.22 ms |
| 恢复 P95 TTFT | 813.13 ms | 206.56 ms |
| 终止请求 CPU 写入，六轮累计 | 15,357,444,096 bytes | 0 |
| 恢复重算 token，六轮累计 | 196,632 | 24 |
| 恢复 H2D，六轮累计 | 0 | 7,678,722,048 bytes |

平均恢复 TTFT 降低 **75.80%**。同设备和 CPU 预算下减少低价值备份，
保住可复用状态；该对照不主张 HBM 减少。8,192-token 整块输入在该版本
prefill 策略下可能缺少更早状态快照，需要回退重算，因此不外推任意边界收益。

### 双卡会话路由与分层缓存

双卡对照沿用官方 `consistent_hash`、TP=1/DP=2、BF16、eager、同步调度、
Mamba `align`，最大上下文 16,384、最大序列数 8、batch budget=8,192。
每轮准备八个会话、插入十六个终止请求，再恢复原八个会话；输入 8,193 token、
输出 8 token。两个种子各两轮，普通与选择性备份反转执行顺序，预算按每卡列出。

| 每卡设备 KV | 策略 | 每卡 CPU 预算 | 恢复平均 TTFT（ms） | 恢复 P95（ms） |
| --- | --- | --- | ---: | ---: |
| 1 GiB | APC | 0 | 772.96 | 793.17 |
| 1 GiB | 普通 CPU 备份 | 2 GiB | 768.68 | 775.14 |
| 1 GiB | 选择性 CPU 备份 | 2 GiB | **152.13** | **160.35** |
| 2 GiB | APC | 0 | 767.11 | 776.33 |
| 2 GiB | 普通 CPU 备份 | 2 GiB | 795.32 | 818.59 |
| 2 GiB | 选择性 CPU 备份 | 2 GiB | 185.38 | 213.88 |
| 4 GiB | APC | 0 | 769.15 | 781.28 |
| 8 GiB | APC，缓存充足参照 | 0 | **134.83** | **147.56** |

同为每卡 1 GiB 设备 + 2 GiB CPU，选择性备份使恢复 TTFT 降低 **80.21%**。
四轮中，终止请求累计 CPU 写入从 **20,476,592,128 字节降为零**，恢复重算
从 **262,176 降为 32 token**，实际 CPU 读回 **10,238,296,064 字节**。

与每卡 8 GiB APC 参照相比，每卡 1 GiB 选择性备份的设备 KV 预算降低
**87.5%**，双卡 HBM 采样峰值 **61,814 → 47,454 MiB**，减少 **14.02 GiB**。
代价为双卡合计 **4 GiB CPU 预算**，平均恢复延迟增加 **17.30 ms**，P95
增加 **12.79 ms**。每轮总耗时为 47.46 → 47.51 秒。

这些是相同输入恢复的顺序压力结果。预算组顺序固定，不将小幅速度差异归因于
池大小；1 GiB 仅为最小已测预算。五秒采样可能遗漏瞬时峰值，不等于分配器
精确高水位，也不代表并发容量或官方 AgentX 整体收益。

## 双平台增长上下文与分支结果

增长负载使用 Qwen3.5-9B BF16、双卡 TP1/DP2、官方 `consistent_hash`、
eager、同步调度、Mamba `align`。CUDA 使用 FlashAttention 与官方 CPU
连接器，Ascend 使用对应 NPU 搬运实现。两个平台分别比较本平台的 8 GiB
APC 参照，不比较跨平台输出或据此做硬件排名。

每条轨迹三轮、每轮新增 2,048 token，固定输出 8 token；普通增长基础长度
4,097 token，非整块边界 4,209 token，分支基础长度 6,145 token，最长
10,241 token。每轮先增长，再插入终止请求造成自然压力，最后恢复相同输入。
历史 token 保持精确前缀；这属于受控生命周期负载，不是自主多轮任务质量评估。

### 设备容量与恢复代价

串行增长下，选择性备份的小设备池与每卡 8 GiB APC 比较，两个种子的峰值
等权平均如下。设备内存减少来自缩小池预算，选择性备份用于控制恢复代价：

| 平台 / 选择性预算 | 双卡 HBM 峰值均值 MiB，基线 → 选择性 | 减少 GiB | 新增 CPU KV 总预算 | TTFT ms，基线 → 选择性 |
| --- | ---: | ---: | ---: | ---: |
| H100，1 / 2 GiB | 54,760 → 40,956 | 13.48 | 4 GiB | 104.87 → 124.58 |
| H100，4 / 4 GiB | 54,760 → 46,724 | 7.85 | 8 GiB | 104.87 → 110.60 |
| Ascend，4 / 4 GiB | 61,825 → 53,637 | 8.00 | 8 GiB | 134.72 → 175.52 |

同设备池的普通与选择性备份不能据此声称不同显存容量。CPU 配置预算不等于
实测 PSS，HBM 五秒采样可能遗漏峰值。当前未建立并发长尾、十六会话或并发
共享分支的同等服务质量容量收益，也未验证工具等待主动迁移或预取。

## 面向长生命周期与分支的统一方案

应用数据和 KV 派生缓存使用同一组生命周期信号，但采用独立的数据格式、
引用和容量预算。原始证据仍有消费者时不能因 KV 淘汰而删除；KV 丢失允许
从保留的精确输入重算。工具正文外置也不意味着模型 KV 已经卸载。

### 生命周期与资源所有权

后续统一控制器采用应用事件驱动策略，不在请求正文中猜测工具是否结束。事件至少带会话、
分支、版本和单调序号；工具事件还带调用标识，旧调用的迟到完成不能覆盖新状态。
事件重放需要幂等。初期只接应用当前已知的信号，不使用未来轨迹推断真实收益。

| 事件或状态 | 工具数据动作 | KV 动作与限制 |
| --- | --- | --- |
| 活跃推理 | 保留当前证据与有界读取窗口 | 官方引擎拥有计算中的物理块；外部策略不能释放活跃引用 |
| 创建分支 | 子分支继承不可变对象引用，后续修改生成新版本 | 精确公共前缀使用官方 APC；私有后缀独立分配；支持的可写共享尾页执行 CoW |
| 工具等待 | 流式存储大结果，记录预计返回窗口 | 按压力和复用价值决定备份；普通已完成 HTTP 请求的块本来就可回收，不能重复计入释放量 |
| 准备恢复 | 按需取回证据切片 | 先用官方按需恢复；预取须有独立配额和截止时间，不能长期占住设备空间 |
| 分支结束或取消 | 只释放该分支引用，兄弟分支仍可读取 | 释放该请求及传输持有的引用；公共前缀仍由官方缓存管理 |
| 阶段完成 | 应用显式声明下一阶段所需的完整 live set，再回收其余对象 | 按未来已知复用范围限制新增备份；该字段不会删除已存在的缓存副本 |
| 会话结束 | 最后一个所有者释放后回收无持久保留要求的对象 | 停止该会话的新备份、取消未开始的预取；不误删其他会话共享的缓存 |

设备计算引用、传输期间的临时引用、应用对象的持久所有权必须分开。
迁移只有在数据复制完成、版本仍一致且目标可读取后才算成功；提交前源数据不得
被写坏。崩溃或取消必须释放临时资源；备份失败回退到官方淘汰/重算，不返回半份
混合状态。应用对象过期与缓存容量淘汰分别处理，不能以“冷”推断原文已无用途。

### 分支共享与混合模型

共享以实际 token 前缀及模型配置一致为条件，不能按语义相似或 session ID
直接复用 KV。模型权重、位置编码、适配器、缓存布局、分片及精度不兼容时重算。
共享的物理页只计一次，私有后缀、尾页复制、保留的循环状态和传输缓冲分别计量。
输入文本缩短、设备读取流量下降与物理页共享是三个独立收益。

CUDA 固定基线已有完整页 APC 和部分命中尾页 CoW；继续使用现成块管理器与复制
路径。Qwen3.5 的 GDN/Mamba 状态会更新，恢复必须选取与 full-attention KV
一致的状态边界，不能把两个分支的循环状态拼接。目标平台不支持相应 CoW 或状态
往返时保守重算，不能只搬 attention KV 就报告混合缓存命中。

应用工具数据已有 `PagedToolStore`：内容寻址的不可变页、分支继承引用、范围修改
和最后引用回收。等长修改可共享未变页；改变长度导致页边界移动时共享率可能下降。
不再实现另一套同用途的引用计数器；策略层只决定何时调用既有生命周期接口。

### Prompt 与工具数据

稳定 system prompt、工具 schema 和公共上下文保留稳定顺序和版本标识；优先使用
现有精确去重，不每轮重写公共前缀破坏 APC。工具按需选择或语义摘要改变模型可见
信息，必须另做任务质量、证据回溯和工具可发现性检查，不混入原样 AgentX 对照。

大工具结果以不可变快照保存，模型获取小型描述和读取句柄，按范围或查询加载。
应用须允许找到被移出当前 prompt 的历史句柄。生产、存储、检索全链路都要限制
缓冲大小；“完整读入后再分页”仍会产生主存峰值。文件读取的选中内容已采用
有界缓冲和流式入库，实测见 [工具数据结果](agentrix_cross_platform_optimizations.md#六-工具页面与主存实验)。
命令输出和搜索输出的完整捕获、长期累积的事件列表尚需后续处理，不能据此宣称
所有工具或无限长会话已经获得固定主存上限。

### 分层预算与策略

设备活跃工作集、设备可淘汰缓存、CPU KV 副本、外部 KV 数据、工具对象、元数据
和临时缓冲分别设预算。CPU/磁盘容量是显式成本，不作为免费的无限后备。
固定设备池内的动态回收用于重分配给新请求；真正降低板卡占用要缩小预分配池并
验证同等服务质量，不声称单次淘汰会自动归还 HBM。

初期策略采用可解释规则：已知会复用的前缀允许备份，已知无后继需求的范围跳过
备份；不知道时沿用官方默认。用 `max_offload_tokens` 控制前缀备份范围，不把
它当成 GPU 驱逐或 CPU 删除 API。已保存副本的淘汰仍使用官方 LRU/ARC；只有
相对这些基线出现收益，才增加生命周期优先级策略。

工具等待时长只能指导优先级，不能授权删除仍有所有者的原文。迁移要综合剩余
等待窗口、实际复制带宽、重算代价、预计复用次数与当前压力；短等待、低压力或
无法在恢复前完成复制时避免额外搬运。用高低水位及最短驻留时间抑制来回迁移。
预取先预留容量，再发起传输；额度包括目的设备块、CPU 固定页和在途数据，恢复
取消后及时撤销。默认先按需恢复，提前预取另作对照，不一次混入多个变量。

### 平台分工

| 层次 | 共用机制 | 后端差异 |
| --- | --- | --- |
| 应用数据 | 不可变快照、页面共享、阶段回收、按需读取 | 不依赖 CUDA 或 CANN |
| 生命周期策略 | 会话身份、终止语义、选择性备份上限 | 由官方请求接口传递 |
| CUDA KV | 官方 APC/CoW、CPU offload 与按需恢复 | CUDA 复制流、事件及混合状态布局 |
| Ascend KV | 官方 APC 与 NPU offload 路径 | NPU 搬运、事件、状态粒度及插件版本约束 |
| DTK | 可复用应用策略和预算设计 | 尚未完成后端适配与硬件验证 |

两平台均已建立表中配置下的恢复与容量结果。跨设备迁移不能假定 KV 字节布局
兼容；模型、位置编码、缓存布局或精度不兼容时，应在目标设备重新计算。
工具等待迁移、预取与外部 KV 存储在统一方案中仍是待实现部分。

## 已有方案的取舍

| 方向 | 当前结论 |
| --- | --- |
| 工具数据外置、共享、回收、流式入库 | 保留；已建立活动 KV、存储或 RSS 收益，代价见 [工具数据报告](agentrix_cross_platform_optimizations.md#六-工具页面与主存实验) |
| 官方 APC、页共享、CoW 与 CPU 备份 | 沿用框架能力；终止提示在双平台上减少写入和恢复重算 |
| Ascend 稀疏混合状态保留 | 旧版适配，同容量下有单次服务级改善；不减少预分配池，详见 [Ascend 专题](agentx_ascend.md) |
| ForkAttention | Ascend 特定长前缀图模式有执行收益，但增加工作区；不列为内存容量优化 |
| 自定义路由、外部 checkpoint 提示、私有准入绕行 | 已撤回，未建立优于当前官方方案的整体收益 |
| 历史 residency/placement、proactive backup、LMCache FORK_AWARE | 当前组合未接通或缺少有效对照，不计为已有成果 |
| 累计工具上下文预算 | 未满足任务质量要求，不作为默认优化 |
| 工具等待主动迁移、恢复前预取、磁盘 KV 分层 | 后续方向，不列入已有收益 |

无提示 CPU offload 的官方 AgentX 对照未建立跨种子的稳定整体收益；扩大 CPU
池的诊断也不足以证明稳定改善。官方 trace 的轮次结束不能可靠替代应用终止
提示，受控选择性备份的收益不外推到这些配置。

实验方法与入口见 [benchmark 说明](../benchmark/README.md#controlled-kv-lifecycle-probe)；
跨平台贡献与关键结果见 [技术总文](agentrix_cross_platform_optimizations.md)。
