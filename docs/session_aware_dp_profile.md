# Session-Aware Data-Parallel Routing Profile

## Summary

Agentrix now provides a session-aware policy on top of vLLM's existing internal
data-parallel load balancer. It is selected instead of, rather than composed
with, the existing prefix-aware policy. First turns retain native load
balancing; follow-up turns prefer the rank that most recently served the
session, subject to cache-residency and overload guards.

On a two-replica Qwen3-VL-8B workload with 12 concurrent agent sessions, the
new policy reduced median first-turn batch makespan by 28.4% and increased
first-turn throughput by 39.7%. For follow-up turns it raised local KV reuse
from 92.5% to 98.0%, reduced median batch makespan by 45.0%, and increased
throughput by 81.9%.

This profile intentionally isolates local DP routing. LMCache and Mooncake were
not enabled, and the external KV-transfer counter remained zero. The later
[GPU residency feedback profile](dp_kv_placement.md) covers actual GPU eviction
events and a separate CPU/Mooncake integration run.

## Implementation

Set one mutually exclusive policy with:

```bash
VLLM_AGENTRIX_DP_ROUTING_POLICY=session_aware
```

Requests may provide the following `vllm_xargs`:

```json
{
  "agentrix_session_id": "conversation-42",
  "agentrix_turn": 2,
  "agentrix_history_tokens": 3072
}
```

The policy implements these decisions:

1. A zero-valued turn uses vLLM's native queue-based rank choice.
2. A follow-up with a live session mapping tries the mapped rank.
3. Without a session ID or live mapping, the router uses its longest known
   logical prefix as the affinity hint.
4. It falls back to the native rank if too little of the expected history is
   believed resident, or if the affine rank exceeds the load/work bounds.
5. A rerouted request moves the session mapping to the new rank. Session
   mappings share the warm-prefix TTL and entry bound and are cleared on a
   prefix-cache reset.

Chat completions infer `agentrix_turn` from prior assistant messages when the
client does not supply it. The legacy
`VLLM_FORK_ATTN_DP_PREFIX_ROUTING=1` variable remains a compatibility alias for
the `prefix_aware` policy.

The default cache-residency signal remains logical. The optional
`VLLM_AGENTRIX_DP_KV_EVENTS=1` path consumes vLLM GPU events for supported
plain-token requests; it does not use LMCache events as GPU residency evidence.
`agentrix_history_tokens` supplies an additional lower-bound check in both modes.

## Workload

Each of five trials performs a physical prefix-cache reset and then sends:

1. One 2,048-token request to prime a shared system prefix.
2. Twelve concurrent first turns, each containing the shared prefix plus 1,024
   session-private tokens.
3. Twelve concurrent follow-up turns, each containing its full 3,072-token
   session history plus 64 new tokens.

Every request generates one token. Requests are launched 1 ms apart. Server
Prometheus counters, rather than the completion API's optional usage detail,
measure local compute and cache-hit tokens at each phase boundary.

The workload is generated by
`benchmark/scripts/benchmark_agent_session_dp.py`; the matched server runs and
GPU sampling are managed by
`benchmark/scripts/run_agent_session_dp_profile.sh`.

## Results

Values are medians across five trials.

### First turns

| Metric | Prefix-aware | Session-aware | Change |
| --- | ---: | ---: | ---: |
| Local cached-token rate | 61.11% | 61.11% | 0.00 pp |
| Mean TTFT | 708.3 ms | 523.7 ms | -26.1% |
| P50 TTFT | 780.8 ms | 523.6 ms | -32.9% |
| P95 TTFT | 917.0 ms | 659.7 ms | -28.1% |
| Batch makespan | 929.4 ms | 665.2 ms | -28.4% |
| Throughput | 12.91 req/s | 18.04 req/s | +39.7% |

Both arms reused exactly 22,528 tokens and computed 14,336 tokens per trial.
The latency difference therefore comes from distributing independent first
turns instead of allowing shared-prefix affinity to shape their placement.

### Follow-up turns

| Metric | Prefix-aware | Session-aware | Change |
| --- | ---: | ---: | ---: |
| Local cached-token rate | 92.52% | 97.96% | +5.44 pp |
| Mean TTFT | 169.6 ms | 118.2 ms | -30.3% |
| P50 TTFT | 150.2 ms | 121.9 ms | -18.8% |
| P95 TTFT | 258.1 ms | 141.7 ms | -45.1% |
| Batch makespan | 269.6 ms | 148.3 ms | -45.0% |
| Throughput | 44.51 req/s | 80.94 req/s | +81.9% |

Session-aware routing reused exactly 36,864 tokens per trial: all twelve
requests found their 3,072-token histories and computed only their 64-token
extensions. Prefix-aware routing reused 32,768-35,840 tokens because concurrent
load/work guards sometimes selected a rank containing only the shared portion.

## Router CPU Cost

A separate 5,000-decision microbenchmark used 12 resident sessions, 3,072-token
histories, 64-token follow-ups, and two ranks.

| Policy | Mean | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: |
| Prefix-aware | 52.49 us | 51.21 us | 54.07 us | 95.36 us |
| Session-aware | 55.67 us | 54.94 us | 58.45 us | 85.39 us |

The direct session lookup adds about 3.18 us per decision. Its 55.67 us mean is
approximately 0.011% of the measured session-aware first-turn P50 TTFT.

## GPU and Memory Sampling

One-second `nvidia-smi dmon` samples observed 100% peak SM utilization on both
GPUs in both arms. Peak sampled framebuffer allocation was 26,879/26,827 MiB
for prefix-aware and 26,431/26,451 MiB for session-aware. The router itself is
frontend CPU state and does not change the configured KV-cache capacity, so
this coarse difference should not be interpreted as a memory-capacity saving.

Prometheus gives the useful memory-management result: session-aware follow-ups
recomputed 768 tokens per trial, versus a median 2,816 tokens for prefix-aware,
while retaining balanced first-turn work.

## Validation and Limits

- Targeted router and request-protocol tests: 36 passed.
- Both arms completed all 125 measured requests and five cache resets.
- No request or inference errors occurred during either workload. vLLM logs an
  `EngineDeadError` from its output-handler task only after the runner sends
  SIGTERM during normal teardown.
- The completion API in this build did not populate its optional
  `prompt_tokens_details.cached_tokens`; phase metrics therefore use the
  authoritative per-engine Prometheus token-source counters.
- The benchmark is prefill-heavy and uses a uniform two-turn session shape. It
  does not establish gains for decode-heavy traffic, skewed session lengths,
  high overload rates, multiple API frontend processes, or external KV
  storage.
