# Agentrix：NVIDIA 优化结果与 vLLM-Ascend 适配方案

## 1. 结论摘要

Agentrix 已实现覆盖工具数据读取、上下文准入、分支共享和阶段回收的内存管理机制。在单张 H100、Qwen3-8B BF16、固定 2 GiB KV 池的多分支工具工作流中，**KV 工作集峰值降低 53.2%，同一批任务完成速率达到原来的 3.59 倍，全部工作流与分支均正确完成**。

实现集中在四处：工具结果按需进入模型，分支共享未修改的页面，阶段结束后释放已消费数据，文件读取只保留目标内容。对应结果如下：

| 已完成优化 | 对照场景 | 指标 | 优化前 → 后 | 降幅 |
| --- | --- | --- | --- | ---: |
| 工具结果外置、按需检索 | 单张 H100，Qwen3-8B BF16，合成多分支工具工作流 | 采样 KV 工作集峰值，两次运行峰值的中位数 | 1,874.25 → 876.38 MiB | **53.2%** |
| 不同版本共享不可变页面 | 8 MiB 原始报告，8 个分支各修改 32 字符 | 去重后的工具数据存储量 | 72 → 8.03 MiB | **88.8%** |
| 按工作流阶段回收 | 16 阶段，每阶段产生 2 MiB 报告 | 工具数据存储峰值 | 32 → 4 MiB | **87.5%** |
| 文件分块扫描、仅保留所需行 | 从 64 MiB 文件读取 32 行 | 工具进程 CPU 内存峰值 RSS | 177.55 → 22.09 MiB | **87.6%** |

四组实验分别衡量 GPU 工作集、工具数据存储和 CPU 内存。H100 实验还将源报告扩大到两倍：按需读取组仍全部正确完成，完整内联组出现上下文长度超限。

当前实现已通过 **53 项相关测试**，覆盖历史快照、分支拥有权、回收原子性、序号迁移、工具文本一致性及 Coding Agent runner，配有闭环模型测试与独立内存 Benchmark。

Ascend 版本以 **vLLM-Ascend** 为实现主体。先把项目已有的 ForkAttention 迁移到 NPU：提取物理前缀 planner，编写 Ascend C 分段 attention 与归并算子，接入原生 KV 布局、FIA 回退和 ACLGraph；再处理分支组调度、TP/DCP 及 Mooncake 缓存恢复。第 6—11 节说明具体代码位置、实现方法和测试。

## 2. 技术贡献与度量方式

### 2.1 内存和数据占用分别统计

| 指标 | 含义 | 本报告的使用方式 |
| --- | --- | --- |
| GPU/NPU 预分配池 | 推理引擎预先保留的 KV 容量 | 固定容量作为对照条件 |
| KV 工作集 | 被运行请求占用、当前不能直接复用的物理块 | 反映固定池内还可容纳多少工作 |
| 工具数据存储量 | 外置快照中唯一内容页面的 UTF-8 字节数 | 不包含数据库元数据、日志或页缓存 |
| SQLite 文件大小 | 数据及索引等实际文件占用 | 与唯一内容字节数分别报告 |
| CPU RSS | 进程驻留主存峰值 | 明确是工具进程还是完整推理服务 |
| 搬运缓冲 | gather/scatter、格式转换、异步传输使用的临时空间 | Ascend 候选优化需要单独测量 |

**已完成的优化重点针对实际工作集。** 在预分配池固定时，减少占用块可以把容量留给更多活跃请求及其上下文。板卡预留量与任务实际使用量分别统计；容量提升通过可完成的任务、数据规模和并发来衡量。

### 2.2 已实现的四项管理机制

| 机制 | 原有开销来源 | Agentrix 的改变 |
| --- | --- | --- |
| 工具数据按需进入上下文 | 每个分支反复携带完整工具报告 | 保留完整外部快照，模型检索并读取必要证据 |
| 不可变页面共享 | 每个分支版本各存一份完整数据 | 共享未变化页面，仅保存修改涉及的页面 |
| 显式生命周期回收 | 中间结果累积到整个 session 结束 | 按仍存活的消费者保留数据，在阶段检查点释放过期引用 |
| 文件流式读取 | 为少量目标行分配全文和全部行对象 | 使用固定扫描缓冲，仅收集需要返回的内容 |

这四项机制分别控制**进入 KV 的数据量、分支复制量、历史保留量和瞬时分配量**，对应 Agent 长生命周期与多路径执行中的四类内存增长来源。

### 2.3 实现与基线

vLLM 原生前缀缓存、分页 KV 共享、已有 CPU offload，以及 Mooncake/LMCache 已提供的缓存与传输能力，不计为 Agentrix 新实现。报告中的模型实验保持 BF16，不把量化节省计入收益。

## 3. NVIDIA 环境下的模型实测

### 3.1 工具结果外置与按需加载

**动机：** Agent 执行构建、检查或检索工具后，往往只需要其中少量证据。把完整报告重复放入每个分支，会让无关工具文本也产生 KV。

**实现：** 将完整报告保存在不可变快照中，向模型提供句柄和检索工具，由模型选择搜索或读取的内容。历史快照不依赖原始文件继续存在。分支共享快照引用，并在最后一个拥有者释放后回收。

完整工具文本保存在模型外，必要证据进入 prompt 后才产生 KV。这使上下文占用与模型当前需要的信息量相匹配。

#### 对照条件

| 项目 | 设置 |
| --- | --- |
| 设备 | 同一服务器、同一张 NVIDIA H100 PCIe，GPU 1 |
| 模型 | Qwen3-8B，BF16 |
| Attention / 执行方式 | FlashAttention，eager |
| KV 池 | 两组均固定 2 GiB |
| 服务限制 | `max_model_len=14336`、`max_num_seqs=32`、`max_num_batched_tokens=1024` |
| 原生前缀缓存 | 两组均开启 |
| 工作流 | 8 个案例，每个案例 3 个审计分支，随后汇总答案 |
| 输入 | 每个案例两份合成 build/check JSONL 报告，每份 128 行 |
| 并发 | 4 个工作流、最多 12 个模型请求 |
| 随机种子 | `20261020`，是固定种子，不是实验日期 |
| 正式测量 | inline、paged、paged、inline；每种方式两次 |

两组使用相同报告、工具和答案检查规则。模型提出不一致的分数/决策时，校验器只检查公开规则，不读取隐藏答案。实验启用校验失败后的原文恢复，恢复、重试、token 和耗时全部计入；每次 paged 测量均发生两次恢复。

#### 实测结果

| 指标 | 完整报告内联 inline | 外置检索 paged |
| --- | ---: | ---: |
| 两次采样 KV 峰值，blocks | 839 / 827 | 389 / 390 |
| 两次采样 KV 峰值，MiB | 1,887.75 / 1,860.75 | 875.25 / 877.50 |
| 峰值中位数，MiB | 1,874.25 | 876.375 |
| 每次运行完整工作流正确数 | 8/8、8/8 | 8/8、8/8 |
| 每次运行分支正确数 | 24/24、24/24 | 24/24、24/24 |
| 错误 / 抢占 | 0 / 0 | 0 / 0 |
| 每次运行输入 token 总数 | 653,025 | 42,108 |
| 完成同一批工作流的中位耗时 | 29.74 s | 8.29 s |
| 实际观察到的并行运行请求峰值 | 5 / 4 | 12 / 12 |
| GPU 板卡占用采样峰值 | 18,643 MiB | 18,643 MiB |

在该负载下，KV 工作集下降 **53.24%**，输入 token 减少 **93.55%**，批次完成时间减少 **72.11%**，任务完成速率达到原来的 **3.59 倍**。两种方式均保持全部任务正确完成；paged 组在固定 KV 池内达到 12 个请求同时运行。

此模型配置每 token 的 BF16 KV 为 144 KiB，每块 16 token，即 2.25 MiB。表中内存由实际占用块数换算，采样间隔约为 70–90 ms。

**收益原因：** 按需检索减少了进入 attention 的工具文本，同时降低 prefill 输入量和活动 KV 占用；固定容量的池能够同时接纳更多请求。

**适用场景：** 大型构建日志、检查报告、检索结果等工具输出，尤其是多个分支需要访问同一份数据、每个分支只使用其中部分证据的工作流。

### 3.2 固定资源下处理两倍源数据

在相同 2 GiB KV 池和 14,336 token 请求窗口下，将源报告从 128 行增至 256 行：

- paged 完成 8/8 工作流、24/24 分支，错误为 0。
- inline 出现上下文长度超限。

在这组测试中，同样的模型窗口和 KV 池支持了两倍源数据，并保持完整任务正确率。原始报告保留在模型外，模型每次只读取需要的部分；attention 窗口仍为 14,336 token。

## 4. 当前项目的 CPU 与存储实测

本节均为同一本机上的 A/B，各组独立进程、交替顺序、每种方式两次。环境记录为 Linux x86_64、Python 3.11.15；没有执行 GPU 推理。

### 4.1 分支快照共享不可变页面

**动机：** 分支修改报告中的少量内容时，重新保存整个结果会产生大量重复数据。

**实现：** 工具文本划分为 4,096 字符页面，按内容哈希共享。分支继承引用；等长修改仅引入变化页面。`put_stream`、`replace_range` 避免先在 Python 中组装整个新版本。

**实验：** 8 MiB 原始报告，8 个独立分支分别修改 32 字符，同时保留原始版本及全部分支版本。

| 指标 | 私有页面基线 | 共享页面 | 变化 |
| --- | ---: | ---: | ---: |
| 唯一有效载荷 | 72.00 MiB | 8.03125 MiB | −88.85% |
| SQLite 文件 | 82.71 MiB | 15.03 MiB | −81.83% |
| 分支更新耗时，含分配采样开销 | 0.374 s | 0.771 s | 增加约 106% |

9 个历史版本均通过完整 SHA-256 校验，释放所有 session 后数据全部回收。**9 个完整版本共占 8.03 MiB 有效载荷**；代价是本组实验中的分支更新耗时增加。

对于页面边界稳定的修改，存储增长由“分支数 × 完整报告”变为“原始报告 + 各分支变化页面”。本例已接近保留一份 8 MiB 原始数据的容量下限，后续重点可转向不等长插入下的页面复用和跨层副本管理。

### 4.2 阶段结束后回收已消费数据

**动机：** 长生命周期工作流如果只在整个 session 结束时释放数据，会持续积累已经消费完的工具中间结果。

**实现：** 阶段检查点接受工作流显式声明的完整保留集合。删除当前拥有者的过期引用；尚未完成的分支仍保有自己的引用，最后一个拥有者释放后才删除页面。无效句柄使操作原子失败，观察记录的序号保持单调。

**实验：** 16 个阶段各产生一份唯一的 2 MiB 报告及小型持久状态。验证分支延迟一个阶段读取完整报告，此后未来阶段只需要持久校验状态。两组都启用同一页面共享实现，只改变回收时机。

| 指标 | session 结束时回收 | 按阶段回收 | 变化 |
| --- | ---: | ---: | ---: |
| 数据存储峰值 | 33,555,950 bytes | 4,194,539 bytes | −87.50% |
| SQLite 文件峰值 | 41,250,816 bytes | 5,228,544 bytes | −87.33% |
| CPU RSS 峰值 | 26,272 KiB | 26,228 KiB | 基本不变 |

16 份报告均完整读取，最终校验链一致，最终存储全部回收。**工作流执行到第 16 阶段时，数据峰值仍控制在约两份活跃报告的大小**，数据峰值由 32 MiB 降到约 4 MiB，进程 RSS 保持稳定。

该机制把数据保留范围从“全部已执行阶段”收缩到“仍有消费者的活跃阶段”。工作流显式声明保留集合，分支引用保证延迟读取正确；当前约 4 MiB 峰值对应两份同时活跃的报告，已经与实际依赖相匹配。

### 4.3 实际工具路径中的文件流式读取

**动机：** 原实现即使只读取少量行，也会执行整个文件的 `read_text().splitlines()`，同时产生全文和全部行对象。

**实现：** 按 65,536 字符扫描，仅保留目标行；保持总行数、行号、文本、换行处理和工具输出语义。

**实验：** 同一个 64 MiB 文件，524,288 行；读取第 1,001–1,032 行，最终输出 4,326 bytes。

| 指标 | 全文读取 | 分块扫描 | 变化 |
| --- | ---: | ---: | ---: |
| 工具进程 RSS 峰值 | 177.55 MiB | 22.09 MiB | −87.56% |
| 读取期间 Python 分配峰值 | 156.47 MiB | 0.263 MiB | −99.83% |
| 单次工具读取时间 | 96.79 ms | 55.26 ms | −42.91% |

RSS 与耗时在未启用 `tracemalloc` 的第一次读取中采集；Python 分配峰值由第二次读取独立测量，避免把采样器自身开销计入 RSS 收益。四次进程运行的输出哈希、长度和截断标记一致。

**流式读取消除了由文件总大小引起的全文临时副本。** 扫描缓冲固定为 65,536 字符，结果内存随返回内容增长；工具输出逐字保持一致。为返回精确总行数仍需扫描完整文件，本项优化直接降低的是工具进程的分配量、RSS 和读取耗时。

## 5. 测试口径与验证进度

上述成果按以下口径使用：

- **四组独立消融。** H100 实验测试工具数据提供方式，后三组为本机 CPU/存储测试；降幅分别报告，不叠加为统一百分比。
- **模型测试范围。** H100 使用合成多分支工具工作流和同一服务栈，两组均开启原生 APC。53.2% 与 3.59 倍对应这组负载；官方 AgentX 及独立原版 vLLM 0.28.0 的整体对照仍待完成。
- **峰值与容量。** KV 数字为定时采样峰值，可能遗漏采样间隔内的短峰值。观察到的并发和两倍源数据实验用于说明容量效果，尚未搜索最大并发边界。
- **正确性。** 模型实验保持全部已测工作流与分支正确，CPU 实验检查数据完整性和工具输出一致性；其他任务分布需使用对应 Benchmark 评估。
- **Ascend 状态。** 第 6—11 节为基于固定版本源码分析提出的实现方案，实测收益在相同 Ascend 硬件与软件配置下单独建立。

其他探索的处理如下：

| 项目 | 当前状态 | 报告处理 |
| --- | --- | --- |
| 累积工具上下文 token 预算 | 第一轮出现基线上下文溢出，候选一轮也有错误；更大同配置对照尚未完成 | 不计入质量保持前提下的 KV 收益 |
| 分支算子、历史调度及 offload 实验 | 部分仍为可选功能；无本报告可核对的当前等配置增益数据 | 不纳入四项收益合计 |
| 无效的 retention / adaptive prefill 实验 | 已在 vLLM `fa702ea44c` 撤回 | 不作为保留优化 |
| 原生 APC、已有 KV COW、CPU offload、量化 | 属于已有基线能力或不在本次范围 | 不算 Agentrix 新贡献 |

累计上下文预算首轮的基线两次均为 0/2 工作流完成，各有 4 个长度错误；候选为 1/2 和 2/2，因此暂不计入成果。后续固定 8 GiB KV 池、24,576 token 窗口的对照，最近一次记录状态为 `waiting_gpu1`。

## 6. Ascend 版本以 vLLM-Ascend 为实现主体

Ascend 适配应落在 **vLLM-Ascend**。vLLM 负责请求调度、分页 KV 和模型执行接口；vLLM-Ascend 负责 NPU attention、模型运行器、ACLGraph、设备算子和通信接入；Agentrix 提供工作流依赖、分支关系及数据保留信息。ForkAttention 的 NPU 后端需要接入这条执行链。

以下接口分析最初参考 vLLM-Ascend 提交 `1af15cce1993`。当前适配基线已固定为子模块 `vllm-ascend v0.22.1rc1`（`5f6faa0cb883`），配套上游 vLLM 0.22.1、CANN 9.0.0、PyTorch/torch_npu 2.10.0 和 Triton-Ascend 3.2.1。单张 Ascend 910B1 上已验证 Qwen3-0.6B 推理、ACLGraph、前缀缓存复用与淘汰、自定义算子以及 CPU/NPU 异步搬运。当前项目中的 ForkAttention 已有 CUDA/Triton 实现，Ascend 版本尚待实现；具体迁移以 0.22.1rc1 的接口为准。

### 6.1 当前代码能复用什么

现有 `vllm/v1/attention/backends/fork_attn.py` 中，`ForkAttentionBackend`、`ForkAttentionImpl` 和 metadata builder 都继承 CUDA FlashAttention 对应类，设备检查也明确要求 CUDA。底层 CUDA 算子使用 CUTLASS/CUTE；已有 Triton 路径限定了特定 head size 和 GQA 比例。迁移时需要拆开以下部分：

| 部分 | 处理方式 |
| --- | --- |
| 物理前缀识别、共享段与私有段划分 | 提取为不依赖 CUDA 后端的公共 planner，保留已有正确性检查 |
| 森林增量更新、请求重排与计划失效规则 | 复用逻辑，接入 NPU runner 的当前批次快照 |
| CUDA 的 tile、warp 数及准入阈值 | 按 NPU 核心、片上缓冲和实测成本重新选择 |
| 分段 attention 与结果归并 | 编写 Ascend C 算子，保留相同的数学定义 |
| FlashAttention metadata 与 KV 视图 | 替换为 vLLM-Ascend 的 metadata 和缓存布局 |
| CUDA Graph 捕获与回放 | 接入 vLLM-Ascend 的 ACLGraph 管理器 |

公共 planner 只描述“哪些 query 访问哪些物理 KV 段”。当前 planner 中夹带的 CUDA tile 选择要移到设备侧调度层，避免公共逻辑继续依赖 warp 数、CUDA capability 或 CUDA 缓冲类。

### 6.2 vLLM-Ascend 中需要改的位置

下表中的已有文件均以 vLLM-Ascend 仓库根目录为起点；标为“拟新增”的条目是计划中的代码位置。

| 代码位置 | 现有职责 | 迁移时的改动 |
| --- | --- | --- |
| `vllm_ascend/platform.py` | `get_attn_backend_cls` 选择 GQA、MLA、SFA 等后端 | 增加 ForkAttention 的显式选择与能力检查，防止配置被普通后端映射覆盖 |
| `vllm_ascend/attention/attention_v1.py` | `AscendAttentionBackend`、`AscendMetadata`、KV 写入和 FIA 调用 | 提供原生缓存接口与回退路径；保留一次 KV 写入的执行顺序 |
| `vllm_ascend/attention/fork_attn.py`（拟新增） | — | 实现 NPU Fork backend、metadata builder、混合批次切分及结果回填 |
| `vllm_ascend/worker/v2/model_runner.py` | 请求顺序、序列长度、输入与运行准备 | 向 planner 传入准确的 CPU 块表和长度快照，在图分派前完成容量检查 |
| `vllm_ascend/worker/v2/aclgraph_utils.py` | `ModelAclGraphManager` 捕获、回放和参数更新 | 管理 Fork/FIA 图变体、固定地址工作区和有效段数更新 |
| `csrc/attention/fork_attention/`（拟新增） | — | 放置 Ascend C 分段 attention、归并算子及 host tiling |
| `csrc/torch_binding.cpp`、`csrc/torch_binding_meta.cpp` 及算子构建配置 | 自定义算子绑定、形状推导与编译 | 注册 NPU 算子，声明输出与工作区，接入图编译 |

第一版选择 **普通 GQA、BF16/FP16、单 token decode、单 NPU**，先用 Qwen3-8B 跑通。Prefill、无共享前缀和不满足条件的请求交给原生 Ascend attention。MiniCPM 根据实际模型结构加入；MLA、滑窗和混合状态模型分别适配。

## 7. ForkAttention 如何迁移到 Ascend NPU

### 7.1 先明确它节省的是什么

多个分支引用同一段历史时，原生前缀缓存已经可以让它们引用相同的物理 KV 页。普通 attention 仍可能按 query 分别读取这些页面。ForkAttention 把访问相同页面的 query 放进同一个计算 tile，使搬入片上的 K/V 能被多个 query 使用。

**每个分支的 Q 不同，QK 打分和加权 V 仍须分别计算。** 共享的是 KV 读取和片上数据使用；将多个 query 排成矩阵，还能改善小批量 decode 的矩阵计算形状。已经由原生 APC 共享的 KV 容量，不会因为开启 ForkAttention 再减少一份。

收益首先取决于同一轮中实际同时运行的分支数、共享前缀长度和私有尾部长度。只有两个分支、共享内容很短，或者多数分支还在等工具时，森林构建、query 重排和结果归并可能超过节省的读取时间。因此 NPU 后端需要保留原生路径，并按实际成本选择。

### 7.2 先把 CANN 已有共享前缀能力放进对照

CANN 的 FIA 接口已有 `key_shared_prefix`、`value_shared_prefix` 和 `actual_shared_prefix_len` 参数。本次检查的 vLLM-Ascend 普通 GQA 调用路径没有显式传入这些参数。第一步应检查目标 CANN 版本能否直接覆盖单一共享前缀，连同分页与布局约束一起测试。

这条路径可作为低成本实现和比较基线，但要计入分页 KV 整理为连续前缀张量的时间与额外空间。接口支持共享前缀，也需要通过设备追踪确认它在目标形状下如何复用 KV 读取。

项目现有 planner 还能表示多层共享关系：所有分支共享系统提示，其中一组又共享工具结果，随后各自生成。**自定义 NPU 算子的重点是直接读取分页 KV，并执行这种多层共享森林。** 单一前缀由原生 FIA 已经高效处理的形状，继续使用原生实现。

### 7.3 KV 布局：直接读取 vLLM-Ascend 的页

当前 CUDA 后端从 K/V 交织的逻辑张量中拆出视图。vLLM-Ascend 的普通 GQA 缓存则把 K、V 放在最外层的两个分量中，支持页内按 token 或按 head 排列。已检查的 `AscendAttentionBackend` 声明块大小为 **128 token**。CUDA 测试中的 16-token 页和地址计算不能直接搬过来。

NPU 算子接收 K/V 基址、页号、实际 stride 和有效长度，在 tile 内完成分页寻址。首版固定一种原生支持的布局，另一种布局增加独立寻址分支；避免为了适配 ForkAttention，每轮复制整段 KV。底层地址乘法使用足够宽的整数类型，覆盖大于 4 GiB 的偏移。

共享段只取已经写完的完整页面。末页不足一块时按请求的有效长度处理；分支写入仍由原生块分配、引用计数和 Copy-on-Write 路径维护。不同模型、适配器、缓存组或位置语义的内容不能仅凭文本相同就合并。跨实例恢复后，应先完成本地物理页映射，再构建本地共享计划。

KV 写入沿用 `do_kv_cache_update` 或当前执行路径中的 `reshape_and_cache`，每层每步只写一次。Fork 和 FIA 分别读取同一份更新后的缓存，写入完成事件也继续交给原有 connector 使用。

### 7.4 Ascend C 内核：按共享段组织 Cube、Vector 与搬运

**任务划分。** 一个计算任务处理“一个共享段、一个 KV head、一组 query”。同一 KV head 对应的 GQA query heads 与分支 query 合并成矩阵行。例如 8 个分支、GQA 比例为 4 时，可形成 32 个 query 行；各行仍保留独立的 softmax 状态和输出位置。

**矩阵计算。** Cube 计算 query 与 K 的乘积，再计算概率与 V 的乘积。K/V 按页映射分块搬入，一块数据在该任务中供多行 query 使用。分支很多时拆成多个 query tile；不能宣称整台 NPU 对共享前缀永远只读一遍，因为不同 tile 和核心仍可能重新读取。

**Softmax。** Vector 处理缩放、有效长度掩码、逐行最大值和指数和。使用在线 softmax，在遍历 KV tile 时更新归一化状态和输出累积，避免把完整 attention score 矩阵写到 HBM。最大值、指数和以及输出累积采用 FP32，最终输出转换回模型精度。

**流水。** 通过 Ascend C 的队列和同步机制衔接数据搬入、Cube 乘法、Vector softmax 和结果搬出。KV 双缓冲的大小与 query tile 一起选择：query 行数增加会提高 KV 复用，也会扩大 score、输出累积和片上存储需求。需要按目标设备的 L1、L0 和 UB 容量分配资源，A2/A3 等平台分别确定分块参数。

CUDA 的 CTA/warp 分工、共享内存访问和异步拷贝实现由上述 NPU 流水重写。已有 Triton 算法可作为数值参考；若使用 Triton-Ascend，需要单独检查分页访问、矩阵指令和图捕获支持，不能把 CUDA Triton kernel 直接视为可用的 NPU 实现。

### 7.5 共享前缀与私有尾部怎样合并

一条 query 可能在森林中经过公共前缀、组内共享段和私有尾部。每段算子输出两项：该段归一化后的 attention 向量，以及 softmax 的 log-sum-exp，简称 LSE。

归并时先取这些段的最大 LSE，再计算各段相对它的指数权重，用归一化后的权重对分段输出求和。这样得到覆盖全部有效历史的 attention 结果。**分段输出不能直接相加，也不能做简单平均。** 各实现的 LSE 对数底数必须统一；当前 Triton 路径内部使用以 2 为底的统计，迁移时要明确转换位置。

短尾部尽量合并进同一任务，减少小 kernel 和中间写入；长前缀可以切成多个 KV 段以增加并行度。切分过多会扩大分段输出工作区并增加归并成本，因此 planner 需要同时限制段数和工作区字节。空段、失效 query 行和全掩码行必须单独处理，避免 NaN 进入后续模型层。

### 7.6 Planner 和 ACLGraph 要一起接入

现有 CUDA planner 已支持增量更新：物理前缀不变时保留共享段，只推进私有尾部；请求重排、页面替换或序列回退时重建。这部分应复用到 NPU，避免每步从头扫描长块表。

vLLM-Ascend 的 V2 runner 已维护 CPU 序列长度信息。Fork planner 还需要与同一批次对应的准确块表、query 长度和行映射。读取设备张量再同步回 CPU 会抵消算子收益；应在 runner 处理调度结果时更新主机镜像。异步调度、抢占恢复和 speculative 场景下，长度上界不等于实际有效长度，必须使用可确认的快照或回退。

ACLGraph 接入需要处理以下状态：

- **固定地址。** query 表、段表、块表、有效计数和分段输出工作区在捕获前分配；回放时更新内容。有效段数放在设备缓冲中，超出容量的批次在图分派前换规格或回退。
- **固定执行结构。** 按 query 容量、段数和 tile 规格准备少量图变体。补齐任务由有效计数屏蔽，不能在回放中依赖 Python 循环改变 kernel 数量。
- **计划失效。** 分支结束时清除旧行；页面重新分配时重建相关映射；工作区容量变化时切换对应图。更新流和计算流通过事件保证同一份计划不被提前覆盖。
- **混合批次。** 单 token decode 中满足条件的 query 走 Fork，其余 prefill 和 decode 走 FIA；分别构建子批次 metadata，最后恢复原输出顺序。模型本轮只进行一次 KV 更新。

先在 eager 下跑通分页、分段和归并，再接入纯 decode ACLGraph，最后接混合 prefill/decode 与异步调度。正式对照采用相同图模式；不能用 eager 基线与图模式候选比较后把全部收益归给 ForkAttention。

### 7.7 准入条件按 NPU 成本确定

现有 CUDA 默认要求同组至少 8 个并发 query、至少 16K token 的共同物理前缀。这是已有测试下的选择，NPU 需要重新确定交叉点。

运行时需要比较原生 FIA 耗时，与 planner、metadata 传输、Fork 分段计算、归并和 query 重排的合计耗时。共享前缀越长、同批活跃分支越多，越有利于摊薄这些附加成本；私有尾部增长、分组变碎或分支陆续结束时，应及时切回 FIA。等待更多分支组批也必须设置时间上限。

初始测量覆盖短、中、长共享前缀，2/4/8/16/32 个活跃分支，不同私有尾部长度和多组独立前缀。记录真实 HBM 读取、矩阵计算时间、Vector/搬运等待及工作区峰值，再形成小型准入表。缓存命中率和总 batch size 都不能代替这些指标。

## 8. vLLM-Ascend 中与 ForkAttention 配套的计算优化

### 8.1 减少 metadata 准备中的重复工作

已检查的 `AscendAttentionMetadataBuilder.build` 会从 CPU 的 query 起点重新构造 pinned tensor 并传到 NPU，而公共 metadata 中已有设备侧 query 起点。这是可直接检查的代码位置：确认形状、填充和生命周期一致后复用已有设备缓冲，特殊补齐场景保留独立处理。

Fork planner 同样只上传发生变化的段信息。长共享前缀的块表可保留，私有尾部增长时更新长度和新增页；按批次一次准备，供使用相同缓存布局的层复用。复用范围必须按 attention/KV 组区分，混合模型不能把不同组的计划混用。

衡量的是每步主机准备耗时、Host-to-Device 字节数和同步次数。小模型中这些开销可能占据明显比例，算子变快后尤其容易暴露。

### 8.2 围绕实际调用链选择融合位置

ForkAttention 接收的是完成模型规定的归一化与位置编码之后的 Q/K。首版复用 vLLM-Ascend 原有投影、Q/K norm、RoPE 和 KV 写入，避免在 attention 迁移时同时改动整层计算。

算子稳定后，从追踪结果中检查两类额外成本：一是 Q/K 处理与 KV 写入之间是否反复落 HBM；二是为了分组而产生的 query gather 和 output scatter 是否过重。前者在原生后端尚未融合且语义允许时合并处理，后者优先让 NPU kernel 按 query 索引直接读写，减少完整中间副本。

稠密模型的 MLP 和输出投影继续使用原生高效路径。只有它们在整层耗时中成为主要部分，才按真实矩阵形状调整 tiling 或融合。每项都报告整层及完整轮次的变化，避免一个局部 kernel 的加速被新增搬运抵消。

### 8.3 调度要给共享计算创造条件

ForkAttention 要求分支在同一轮进入计算。框架可提前提供分支组 ID 和父前缀身份，调度器据此识别同组就绪请求。工具未返回的分支不进入执行集合；已经就绪的请求只允许在有限时间内等待同组成员。

已有短请求优先和分块 prefill 继续作为基础。新增决策同时考虑：本轮共享前缀能节省的读取、等待组批的时间、未命中 token 的计算量，以及汇合所需的分支。长历史但短新增内容的续接请求按真实未命中量计费，同时计入 decode 访问长 KV 的成本。

这部分需要分别报告“kernel 更快”和“调度后完整工作流更快”。如果为了凑分支而延长任务完成时间，应缩短等待窗口或直接走原生路径。

## 9. KV 分层管理怎样与 vLLM-Ascend 配合

### 9.1 先统一缓存身份和所有权

vLLM-Ascend 的 NPU 页分配继续由 vLLM KV 管理器负责。Agentrix 维护工作流对历史的保留需求；LMCache/Mooncake 承接选定的 CPU、共享存储和传输接口。三者通过缓存块身份关联，而不是各自维护一份互不知情的 KV 副本。

分支展开时记录共享前缀的消费者，恢复到同一实例时合并在途加载，并让后续请求复用已恢复的本地页。请求正在 attention 中使用的页、仍在传输的页、可以逐出的缓存页分别记账。最后一个工作流引用结束，只能释放本策略持有的引用；页面是否可回收仍以底层所有权和设备完成事件为准。

恢复会改变物理页号。connector 完成回填后，先更新块表及版本，再让 Fork planner 使用新映射。取消请求则撤销未开始的传输，在途传输结束后释放其引用。这样可避免 planner 读到旧页，或 DMA 写入已经分配给另一请求的空间。

### 9.2 压缩恢复过程的临时缓冲

LMCache-Ascend 的部分逐层 connector 在启用中间设备缓冲时，按完整单层 KV 容量初始化缓冲 allocator。对此可改为固定数量的循环缓冲，按有界数据块搬运。连续区间合并传输，离散页按目标布局整理，缓冲复用由传输和计算完成事件控制。

若 attention 仍要求该层所有历史 KV 就绪，分块搬运只减少中间副本，目标 KV 页仍须保留。后续要让 attention 与恢复流式衔接，则必须让分段 attention 等待自己对应的 KV 段，并延迟最终 LSE 归并；这涉及算子和 connector 的共同修改，应在基础恢复路径稳定后再做。

分块大小需要同时控制启动次数、带宽和暂存空间。报告 NPU 临时缓冲峰值、恢复延迟及实际有效带宽，不能只统计缓冲下降。

### 9.3 工具等待期间的预取

先把预计近期使用的数据从外部存储准备到 CPU DDR，再接近模型执行时恢复到 NPU。LMCache-Ascend 已有的 CPU 预取接口可承担前一步；Agentrix 增加的是基于工具状态的时机选择和预算控制。

预测依据来自已观测的工具耗时和当前工作流状态。分支取消、工具失败或下游路径改变时撤销预取；对同一前缀只保留一份在途需求。预取使用独立字节上限，与前台 decode 和 TP/EP 通信竞争时降低优先级。

评估除恢复时间外，还要统计预取后实际使用的比例、提前驻留时长和被挤出的活跃数据。等待窗口长但恢复概率低的历史，更适合留在 CPU 或外部存储。

## 10. 多卡与分布式执行

### 10.1 TP 下先做每张卡内部的 ForkAttention

张量并行（TP）通常按 attention head 切分计算。每个 rank 对自己的 Q/K/V 分片执行本地 ForkAttention，输出投影和原有集合通信顺序保持不变。当前阶段不需要跨卡传输完整 attention score，也不需要把其他 rank 的 KV 拉到本地。

各 rank 需要一致的逻辑分支分组、query 顺序和回退决策，但物理页号是 rank 本地信息，不能拿不同 rank 的页号直接判断共享。图容量或支持条件有一张卡不满足时，在现有分派同步点选择兼容路径，保证各 rank 进入相同的模型执行与通信序列。

TP 增大后，每卡可用的 KV heads 和每个 tile 的 query 行数可能变化，单卡得到的准入阈值也要重测。对于能装入单卡的模型，还应在相同总卡数下比较 TP 与多个独立副本，选择工作流完成效率更高的部署。

### 10.2 DCP 下归并局部 attention，避免搬回整段 KV

解码上下文并行（DCP）把一条请求的历史分散在多个 rank。各 rank 可先在自己持有的 KV 段上执行 ForkAttention，得到每个 query 的局部输出与 LSE，再完成跨 rank 的全局归一化和加权归并。

这一步与单卡分段归并遵守相同规则：先对 LSE 做稳定归一化，再归并向量。直接对各 rank 的归一化输出做 AllReduce 求和会得到错误结果。优先复用 vLLM-Ascend 原有 DCP 归并协议，新增算子需要准确对齐其 LSE 格式、输出布局及缩放约定。

DCP 的通信量与 query 数及 head 维度有关，历史 KV 继续留在原 rank。但共享 query 被分组后的局部计算形状是否合算，仍取决于每卡分片和互联延迟。DCP 放在单卡与 TP 路径完成之后，单独适配其 metadata builder、块表及图模式。

### 10.3 Fanout-aware routing：分支放在哪里

多个分支集中到一个实例，能够共享本地 KV 并形成 ForkAttention 批次；分散到多个实例，可以缩短排队但需要复制前缀。路由器应比较这两项成本，并考虑汇合等待。

具体决策使用父前缀位置、就绪分支数、各实例队列、剩余 NPU 容量和传输带宽。优先把能形成有效 Fork 批次的分支放到同一实例；排队过长时按组拆分到其他实例。每个目标实例合并一次前缀加载，给复制总量和在途恢复设置上限。

后续轮次尽量留在已有缓存的实例，避免长历史反复迁移。对阻塞下一阶段的分支设置有限优先级；全量汇合、任一成功或固定数量结果分别使用框架声明的完成规则，条件满足后取消无用分支。调度器不预测尚未得到的模型答案。

对照至少包括按队列路由、缓存亲和路由、以及加入 Fork 组批和汇合依赖后的路由。指标是完整工作流 P95、共享前缀复制字节、Fork 实际执行比例和每任务卡秒。

### 10.4 P/D 分离与 Mooncake 传输

长冷请求的输入计算（prefill）与后续生成（decode）可以交给不同实例。工具返回后的短续接则先检查历史所在位置：已有本地 KV 且新增输入很少时，送到支持本地续算的实例；远端执行时，把排队、未命中计算和 KV 恢复一起计入成本。

基于 vLLM-Ascend 已有 connector 实现传输，目标 decode 实例为同组分支建立共同的本地前缀映射，再进入 Fork planner。单纯把相同内容恢复到多套独立物理页，会损失现有物理前缀分组的机会；恢复阶段应复用底层缓存身份，而不是等算子阶段再比较文本。

逐层传输需要与 KV 写入完成事件衔接。发送端在对应层可读后发送，接收端在数据完整后计算；共享前缀在同一目标实例合并传输。TP 大小、KV head 分片或缓存布局不同的实例池，先由 connector 完成受支持的转换，再恢复分支关系。

### 10.5 HCCL、KV 恢复和 MoE 不能各自占满带宽

TP 的集合通信、MoE 的专家分发以及 KV 恢复可能竞争同一条链路和 HBM 带宽。应保留前台模型通信的执行顺序，把后台预取、保存和可推迟的恢复限制在独立预算内。分段传输与其他独立微批的计算重叠，所有 rank 的集合操作顺序保持一致。

MoE 继续使用 vLLM-Ascend 已有专家并行、分组矩阵计算和 EPLB。可增加的工作是把专家迁移与 KV 恢复放进同一带宽预算，避免两者同时造成延迟尖峰。工作流阶段对专家负载的预测只有在观测到稳定相关性后才使用，模型 router 的专家选择保持不变。

KVPP 是另一条面向其支持的 MLA/SFA 模型的路线。已检查的实现存在完整层广播和两个整层接收缓冲，可研究按当前必需物理块的并集传输。它与普通 GQA 的 ForkAttention 迁移分别实现；收益分别记为通信字节、接收缓冲和 attention 耗时的变化。

## 11. 实现顺序与测试

### 11.1 先交付可运行的 vLLM-Ascend 后端

| 顺序 | 代码工作 | 完成标准 |
| --- | --- | --- |
| 1 | 提取公共 planner；接入 vLLM-Ascend 后端选择、metadata 和原生 KV 布局 | Qwen3-8B 可运行，非目标请求正常走 FIA，KV 每层每步只写一次 |
| 2 | 实现 Ascend C 分段 attention 与 LSE 归并；比较原生共享前缀接口 | 分页、多层共享、私有尾部和有效长度正确，得到实际 NPU 算子交叉点 |
| 3 | 接入 ACLGraph、固定工作区和增量计划；补齐混合批次 | 图回放中分支增减、页替换和回退正确，附加主机开销可计量 |
| 4 | 加入异步调度与本地分支组批 | 快照和设备执行一致，完整工具工作流出现稳定收益 |
| 5 | 接入 TP、分支组路由和 Mooncake 恢复 | 相同卡数下，工作流完成时间与前缀传输量有明确改善 |
| 6 | 按模型需求扩展 DCP、MoE 通信协调或 KVPP | 各自与对应原生后端进行独立比较 |

内存恢复缓冲的改动可单独推进，最终再与 ForkAttention 组合测试。原生 FIA 已更快的形状留在原生路径，后端选择根据测量结果自动完成。

### 11.2 测试要覆盖实际分支变化

算子测试覆盖不同共享深度、非连续物理页、不足整页的尾部、不同序列长度和多组前缀；同时检查长地址偏移、失效行和数值稳定性。集成测试覆盖分支结束、请求重排、KV 抢占与恢复、混合 prefill/decode，以及图容量切换。

数值比较先对齐原生 Ascend attention，检查输出误差和模型 logits，再检查完整任务正确率。BF16 下归约顺序变化可能改变临界 token 的选择，不能只凭单个 token 不同判定语义错误，也不能只凭 attention 张量误差小就省去任务评估。

端到端使用官方 AgentX 的数据和方法，并保留多分支工具工作流作为专项测试。对目标模型统计每轮有多少 query 实际进入 Fork、共享前缀多长、多少步骤回退、工具等待占多少时间。这些数据能解释算子收益为何传导或没有传导到整个工作流。

### 11.3 对照与输出数据

每组固定 NPU 型号、卡数、互联、模型权重、精度、vLLM/vLLM-Ascend、CANN 和 torch_npu 版本。原生基线启用对应场景中可用的图执行、前缀缓存和通信优化。使用相同输入、工具结果与生成配置，工具耗时通过相同记录回放。

| 层级 | 必须记录的数据 |
| --- | --- |
| 算子 | FIA/Fork 耗时、实际 HBM 读取、分段与归并耗时、临时工作区 |
| 每轮模型执行 | planner、metadata 传输、图回放、非 attention 层、通信等待 |
| 内存 | 活动 KV、可逐出缓存、传输缓冲、CPU 与外部存储有效数据 |
| 分布式 | 前缀复制字节、恢复时间、HCCL 等待、每卡有效执行时间 |
| Agent 工作流 | 成功率、完整任务 P50/P95、汇合时间、工具返回后的首 token、每任务卡秒 |

先做短时交替对照确定有效形状，再扩大到 AgentX 与长期工作流。ForkAttention 单项、分层缓存单项、调度单项和组合结果分别呈现，避免把原生能力或不同平台硬件差异计入新增实现。

Ascend 后续工作的第一项交付应是 **可在 vLLM-Ascend 中运行、能够自动回退到 FIA 的 ForkAttention 后端**。在此基础上再接图执行、分支调度与跨实例缓存恢复，逐项给出同硬件下的结果。
