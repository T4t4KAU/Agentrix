## 2. 技术贡献与度量方式

### 2.1 内存和数据占用分别统计

| 指标 | 含义 | 本报告的使用方式 |
| --- | --- | --- |
| GPU/NPU 预分配池 | 推理引擎预先保留的 KV 容量 | 固定容量作为对照条件 |
| KV 工作集 | 被运行请求占用、当前不能直接复用的物理块 | 反映固定池内还可容纳多少工作 |
| 工具数据存储量 | 外置快照中唯一内容页面的 UTF-8 字节数 | 不包含数据库元数据、日志或页缓存 |
| SQLite 文件大小 | 数据及索引等实际文件占用 | 与唯一内容字节数分别报告 |
| CPU RSS | 进程驻留主存峰值 | 明确是工具进程还是完整推理服务 |
| 搬运缓冲 | gather/scatter、格式转换、异步传输使用的临时空间 | Ascend 候选优化需要单独测量 |

**已完成的优化重点针对实际工作集。** 在预分配池固定时，减少占用块可以把容量留给更多活跃请求及其上下文。板卡预留量与任务实际使用量分别统计；容量提升通过可完成的任务、数据规模和并发来衡量。

### 2.2 已实现的四项管理机制

| 机制 | 原有开销来源 | Agentrix 的改变 |
| --- | --- | --- |
| 工具数据按需进入上下文 | 每个分支反复携带完整工具报告 | 保留完整外部快照，模型检索并读取必要证据 |
| 不可变页面共享 | 每个分支版本各存一份完整数据 | 共享未变化页面，仅保存修改涉及的页面 |
| 显式生命周期回收 | 中间结果累积到整个 session 结束 | 按仍存活的消费者保留数据，在阶段检查点释放过期引用 |
| 文件流式读取 | 为少量目标行分配全文和全部行对象 | 使用固定扫描缓冲，仅收集需要返回的内容 |

这四项机制分别控制**进入 KV 的数据量、分支复制量、历史保留量和瞬时分配量**，对应 Agent 长生命周期与多路径执行中的四类内存增长来源。

### 2.3 实现与基线

vLLM 原生前缀缓存、分页 KV 共享、已有 CPU offload，以及 Mooncake/LMCache 已提供的缓存与传输能力，不计为 Agentrix 新实现。报告中的模型实验保持 BF16，不把量化节省计入收益。

## 3. NVIDIA 环境下的模型实测

### 3.1 工具结果外置与按需加载

**动机：** Agent 执行构建、检查或检索工具后，往往只需要其中少量证据。把完整报告重复放入每个分支，会让无关工具文本也产生 KV。

**实现：** 将完整报告保存在不可变快照中，向模型提供句柄和检索工具，由模型选择搜索或读取的内容。历史快照不依赖原始文件继续存在。分支共享快照引用，并在最后一个拥有者释放后回收。

完整工具文本保存在模型外，必要证据进入 prompt 后才产生 KV。这使上下文占用与模型当前需要的信息量相匹配。

#### 对照条件

| 项目 | 设置 |
| --- | --- |
| 设备 | 同一服务器、同一张 NVIDIA H100 PCIe，GPU 1 |
| 模型 | Qwen3-8B，BF16 |
| Attention / 执行方式 | FlashAttention，eager |
| KV 池 | 两组均固定 2 GiB |
| 服务限制 | `max_model_len=14336`、`max_num_seqs=32`、`max_num_batched_tokens=1024` |
| 原生前缀缓存 | 两组均开启 |
| 工作流 | 8 个案例，每个案例 3 个审计分支，随后汇总答案 |
| 输入 | 每个案例两份合成 build/check JSONL 报告，每份 128 行 |
| 并发 | 4 个工作流、最多 12 个模型请求 |
| 随机种子 | `20261020`，是固定种子，不是实验日期 |
| 正式测量 | inline、paged、paged、inline；每种方式两次 |

两组使用相同报告、工具和答案检查规则。模型提出不一致的分数/决策时，校验器只检查公开规则，不读取隐藏答案。实验启用校验失败后的原文恢复，恢复、重试、token 和耗时全部计入；每次 paged 测量均发生两次恢复。

#### 实测结果

| 指标 | 完整报告内联 inline | 外置检索 paged |
| --- | ---: | ---: |
| 两次采样 KV 峰值，blocks | 839 / 827 | 389 / 390 |
| 两次采样 KV 峰值，MiB | 1,887.75 / 1,860.75 | 875.25 / 877.50 |
| 峰值中位数，MiB | 1,874.25 | 876.375 |
| 每次运行完整工作流正确数 | 8/8、8/8 | 8/8、8/8 |
| 每次运行分支正确数 | 24/24、24/24 | 24/24、24/24 |
| 错误 / 抢占 | 0 / 0 | 0 / 0 |
| 每次运行输入 token 总数 | 653,025 | 42,108 |
| 完成同一批工作流的中位耗时 | 29.74 s | 8.29 s |
| 实际观察到的并行运行请求峰值 | 5 / 4 | 12 / 12 |
| GPU 板卡占用采样峰值 | 18,643 MiB | 18,643 MiB |

在该负载下，KV 工作集下降 **53.24%**，输入 token 减少 **93.55%**，批次完成时间减少 **72.11%**，任务完成速率达到原来的 **3.59 倍**。两种方式均保持全部任务正确完成；paged 组在固定 KV 池内达到 12 个请求同时运行。

此模型配置每 token 的 BF16 KV 为 144 KiB，每块 16 token，即 2.25 MiB。表中内存由实际占用块数换算，采样间隔约为 70–90 ms。

**收益原因：** 按需检索减少了进入 attention 的工具文本，同时降低 prefill 输入量和活动 KV 占用；固定容量的池能够同时接纳更多请求。

**适用场景：** 大型构建日志、检查报告、检索结果等工具输出，尤其是多个分支需要访问同一份数据、每个分支只使用其中部分证据的工作流。

### 3.2 固定资源下处理两倍源数据

在相同 2 GiB KV 池和 14,336 token 请求窗口下，将源报告从 128 行增至 256 行：

- paged 完成 8/8 工作流、24/24 分支，错误为 0。
- inline 出现上下文长度超限。

在这组测试中，同样的模型窗口和 KV 池支持了两倍源数据，并保持完整任务正确率。原始报告保留在模型外，模型每次只读取需要的部分；attention 窗口仍为 14,336 token。

## 4. 当前项目的 CPU 与存储实测

本节均为同一本机上的 A/B，各组独立进程、交替顺序、每种方式两次。环境记录为 Linux x86_64、Python 3.11.15；没有执行 GPU 推理。

### 4.1 分支快照共享不可变页面

**动机：** 分支修改报告中的少量内容时，重新保存整个结果会产生大量重复数据。

**实现：** 工具文本划分为 4,096 字符页面，按内容哈希共享。分支继承引用；等长修改仅引入变化页面。`put_stream`、`replace_range` 避免先在 Python 中组装整个新版本。

**实验：** 8 MiB 原始报告，8 个独立分支分别修改 32 字符，同时保留原始版本及全部分支版本。

| 指标 | 私有页面基线 | 共享页面 | 变化 |
| --- | ---: | ---: | ---: |
| 唯一有效载荷 | 72.00 MiB | 8.03125 MiB | −88.85% |
| SQLite 文件 | 82.71 MiB | 15.03 MiB | −81.83% |
| 分支更新耗时，含分配采样开销 | 0.374 s | 0.771 s | 增加约 106% |

9 个历史版本均通过完整 SHA-256 校验，释放所有 session 后数据全部回收。**9 个完整版本共占 8.03 MiB 有效载荷**；代价是本组实验中的分支更新耗时增加。

对于页面边界稳定的修改，存储增长由“分支数 × 完整报告”变为“原始报告 + 各分支变化页面”。本例已接近保留一份 8 MiB 原始数据的容量下限，后续重点可转向不等长插入下的页面复用和跨层副本管理。

### 4.2 阶段结束后回收已消费数据

**动机：** 长生命周期工作流如果只在整个 session 结束时释放数据，会持续积累已经消费完的工具中间结果。

**实现：** 阶段检查点接受工作流显式声明的完整保留集合。删除当前拥有者的过期引用；尚未完成的分支仍保有自己的引用，最后一个拥有者释放后才删除页面。无效句柄使操作原子失败，观察记录的序号保持单调。

**实验：** 16 个阶段各产生一份唯一的 2 MiB 报告及小型持久状态。验证分支延迟一个阶段读取完整报告，此后未来阶段只需要持久校验状态。两组都启用同一页面共享实现，只改变回收时机。

| 指标 | session 结束时回收 | 按阶段回收 | 变化 |
| --- | ---: | ---: | ---: |
| 数据存储峰值 | 33,555,950 bytes | 4,194,539 bytes | −87.50% |
| SQLite 文件峰值 | 41,250,816 bytes | 5,228,544 bytes | −87.33% |
| CPU RSS 峰值 | 26,272 KiB | 26,228 KiB | 基本不变 |

16 份报告均完整读取，最终校验链一致，最终存储全部回收。**工作流执行到第 16 阶段时，数据峰值仍控制在约两份活跃报告的大小**，数据峰值由 32 MiB 降到约 4 MiB，进程 RSS 保持稳定。

该机制把数据保留范围从“全部已执行阶段”收缩到“仍有消费者的活跃阶段”。工作流显式声明保留集合，分支引用保证延迟读取正确；当前约 4 MiB 峰值对应两份同时活跃的报告，已经与实际依赖相匹配。

### 4.3 实际工具路径中的文件流式读取

**动机：** 原实现即使只读取少量行，也会执行整个文件的 `read_text().splitlines()`，同时产生全文和全部行对象。

**实现：** 按 65,536 字符扫描，仅保留目标行；保持总行数、行号、文本、换行处理和工具输出语义。

**实验：** 同一个 64 MiB 文件，524,288 行；读取第 1,001–1,032 行，最终输出 4,326 bytes。

| 指标 | 全文读取 | 分块扫描 | 变化 |
| --- | ---: | ---: | ---: |
| 工具进程 RSS 峰值 | 177.55 MiB | 22.09 MiB | −87.56% |
| 读取期间 Python 分配峰值 | 156.47 MiB | 0.263 MiB | −99.83% |
| 单次工具读取时间 | 96.79 ms | 55.26 ms | −42.91% |

RSS 与耗时在未启用 `tracemalloc` 的第一次读取中采集；Python 分配峰值由第二次读取独立测量，避免把采样器自身开销计入 RSS 收益。四次进程运行的输出哈希、长度和截断标记一致。

**流式读取消除了由文件总大小引起的全文临时副本。** 扫描缓冲固定为 65,536 字符，结果内存随返回内容增长；工具输出逐字保持一致。为返回精确总行数仍需扫描完整文件，本项优化直接降低的是工具进程的分配量、RSS 和读取耗时。

### 4.4 选中大结果的有界缓冲与流式入库（2026-09-28）

上一节解决的是“未选中的文件内容也占内存”。选中的行本身很大时，旧路径仍把
整个结果拼成字符串、编码成 bytes，再送入分页存储。本轮修复这个剩余峰值：
单次扫描文件，选中正文使用 256 KiB 阈值的临时缓冲，超过后写临时文件；得到
精确总行数后，以 64 Ki 字符块输出头部与正文，直接调用已有 `put_stream`。
小结果继续内联；关闭分页时保持原有截断响应及完整内容哈希。

在可访问实验服务器上进行 CPU/存储对照，未加载模型、未占用加速卡。
基线为改动前的实际文件读取代码，候选为当前同一工具路径。两组使用相同文件、
行范围和分页存储；测试 8 / 64 MiB 超长选中行，并保留小结果控制组。
8 MiB 和小结果各两对，64 MiB 各三对，交替先后顺序，共 24 个独立进程。
每进程首次读取测 RSS/耗时，第二次在独立空存储中测 Python 分配峰值。

| 场景 | 进程 RSS 峰值：原实现 → 流式 | RSS 降幅 | 工具耗时：原实现 → 流式 |
| --- | ---: | ---: | ---: |
| 8 MiB，截断响应 | 50.78 → 20.26 MiB | 60.10% | 34.56 → 33.94 ms |
| 64 MiB，截断响应 | 274.94 → 20.25 MiB | 92.63% | 256.92 → 265.11 ms，+3.19% |
| 8 MiB，完整分页存储 | 61.22 → 29.64 MiB | 51.58% | 135.95 → 150.03 ms，+10.35% |
| 64 MiB，完整分页存储 | 285.32 → 29.63 MiB | 89.62% | 1,078.63 → 1,164.55 ms，+7.97% |

表中为各组中位数。大结果的 Python 分配峰值由约 32.04–256.12 MiB 降到
约 **0.444 MiB**；8 MiB 增长到 64 MiB 时，候选的工作缓冲没有随结果同步增长。
小结果耗时为 0.275 → 0.341 ms，增加约 0.066 ms，不记为加速。

所有组的完整内容哈希、响应哈希、长度、分页与截断标记一致。分页组逐块恢复
完整历史快照、核对 SHA-256，释放会话后存储归零。48 项工具/存储回归在本地
及服务器通过，覆盖 Unicode/换行边界、选中超长行、历史恢复、分支引用及配额
失败无残留。代码改变数据传递方式，保持模型可见结果，不涉及提示压缩或模型推理。

该优化以额外临时文件 I/O 换取进程内存下降，按内存收益保留。临时正文可能达到
选中内容大小；OS 页缓存、临时目录介质和整机可用内存不包含在 RSS 降幅内。
正式运行应将临时目录放在有容量预算的存储上；本结果不意味着 CPU 总预留内存、
GPU KV 池、板卡显存或 NPU 吞吐改善。搜索/命令输出仍可能完整捕获，长期事件
列表也未改为有界日志，不能宣称所有工具路径已消除增长。

代码、输入文件、源码哈希、24 份进程结果、测试及诊断日志只在服务器
`${RESULTS_DIR}/memory-lifecycle-20260928/`。完整复现入口见
[应用 README](../application/README.md#paged-tool-snapshots-and-branch-lifetimes)。

## 6. Ascend 当前状态与后续工作的边界

Ascend 实现位于 `vllm-ascend/`，配套 vLLM 0.22.1；CUDA 子模块是另一条运行时分支。

  prefill 分块和 `npugraph_ex`，各自的基线与重复次数分别记录。

  只有特定算子负载收益，官方 AgentX 共享路径未触发，保持默认关闭。
